# MangaNia 技術判断

更新日: 2026-11-12
形式: 追記式の ADR（Architecture Decision Record）

現在の構成は [DESIGN.md](DESIGN.md)、既定値は [PREFERENCES.md](PREFERENCES.md) を参照してください。

## ADR-001: UI は winit + softbuffer + muda

**背景**: 初期設計では libui-ng を候補にしていたが、ZIP のドラッグ＆ドロップ、ネイティブメニュー、CPU 描画を小さくまとめたい。

**決定**: `winit` でイベントループとウィンドウ、`softbuffer` で CPU 描画、`muda` で Windows / macOS のネイティブメニューを実装する。

**理由**: 画像ビューアに必要な機能へ直接アクセスでき、libui-ng の FFI とビルド依存を避けられる。Win7 向けのビルド経路も比較的単純になる。

**影響**: メニューは Windows / macOS のみ。Linux はキーバインドでの操作になる。UI 部品は自前で最小限にする。

## ADR-002: ZIP は zip crate で直接読む

**背景**: 初期設計では libarchive を暫定候補にしていた。

**決定**: `zip` crate を使い、Central Directory を一度だけ索引化してエントリへランダムアクセスする。Stored / Deflate のみを対象とする。

**理由**: ZIP / CBZ に必要な機能へ絞れば依存が小さく、外部 C ライブラリのビルドと Win7 互換性の確認が不要になる。

**影響**: RAR / 7z は対象外。ZIP64 や破損データの扱いは crate と自前の上限チェックに依存する。

## ADR-003: 画像は image crate、JPEG / PNG / WebP のみ

**決定**: `image` crate の JPEG / PNG / WebP デコーダを使い、デコード結果を `RgbaImage` に統一する。

**理由**: まず漫画ビューアとして必要な形式を確実に扱う。外部 C デコーダの FFI を持たずに済む。

**影響**: JPEG 2000、JPEG XL、AVIF、GIF は未対応。縮小デコードは行わず、原寸デコード後に表示サイズへ縮小する。

## ADR-004: 描画は CPU のピクセルバッファ

**決定**: デコード済み画像を `u32` の 0RGB バッファへ描画し、`softbuffer` でウィンドウへ転送する。

**理由**: GPU を必須にせず、Win7 を含む環境で描画経路を単純に保てる。画像ビューアの表示要件では GPU 描画の利点が小さい。

**影響**: 大きな画像の縮小は CPU で行う。表示中は直前のフレームを保持して暗転を防ぐ。

## ADR-005: 自然順ソートは自前実装

**決定**: ファイル名の数字列を数値として比較する自然順ソートを自前で実装し、テストする。

**理由**: `2.jpg` と `10.jpg` の順序は漫画ビューアの基本要件。小さな処理であり、依存追加よりテストで固定する方が扱いやすい。

**影響**: 大文字小文字を同一視し、数字列の先頭ゼロを無視する。仕様を変える場合は `archive.rs` のテストを更新する。

## ADR-006: 設定は TOML を3ファイルに分ける

**決定**: 一般設定を `config.toml`、キーを `keybindings.toml`、マウスを `mouse.toml` に分ける。`serde` + `toml` で読み書きする。

**理由**: 文字列とパスを扱うため手書きパーサでは不足する。設定の責務を分けると、ユーザーが編集する範囲とコードの担当範囲が明確になる。

**影響**: 設定ディレクトリは `dirs` で解決する。キー・マウス設定は初回起動時に既定値で作成する。

## ADR-007: 保存は元画像バイト列をそのまま書き出す

**決定**: 表示中ページの保存では、ZIP 内の元エントリを読み直し、再エンコードせずに書き出す。拡張子は元画像から引き継ぐ。

**理由**: 画質を落とさず、保存処理も単純になる。

**影響**: 保存のたびに ZIP を開き直して索引を作る。大きな書庫では保存に少し時間がかかる。同名ファイルは上書きする。

## ADR-008: 入力は Action に集約し、キー・マウスを設定可能にする

**決定**: メニュー、キーボード、マウスの操作を `Action` に集約し、キーとマウスの割り当てを TOML で変更できるようにする。

**理由**: 操作ごとに実装が分岐すると、メニューとキーの挙動がずれる。設定可能にしても実装の中心を1箇所に保てる。

**影響**: アクション名と既定値の互換性を維持する必要がある。設定ファイルにないアクションは既定値を使う。

## ADR-009: ダブルクリックは保留と遅延で判定する

**決定**: ダブルクリック設定があるボタンでは、シングルクリックのアクションを `double_click_ms` の間だけ保留する。2回目が時間内・近距離ならダブルクリックのアクションだけを実行する。

**理由**: 左クリックが「次のページ」、ダブルクリックが「保存」の場合、シングルクリックを即時実行すると保存前にページが進んでしまう。

**影響**: ダブルクリックを割り当てたボタンは、シングルクリックの反応が判定時間だけ遅れる。ダブルクリックのないボタンは即時のまま。

## ADR-010: 先読みは1ワーカー、キャッシュはページ数とバイト数で制限

**決定**: ZIP 読み出しとデコードを1つのワーカースレッドで行い、現在ページを優先する。キャッシュは `先読み枚数 + 2` ページかつ最大 128MiB とする。

**理由**: 実装を小さく保ちながら、ページ送りの待ち時間とピークメモリを制御できる。

**影響**: 同時デコードは行わない。巨大な画像は先読みせず、現在ページだけを保持する。ディスクキャッシュは持たない。

## ADR-011: 見開きは右→左固定、組は先頭から (1,2)

**決定**: 見開きは現在ページを右、次ページを左に置く。ページ送りは2ページ単位とし、末尾で1ページ余る場合は中央に表示する。

**理由**: 日本の漫画の読み方向に合わせた最小の実装とする。

**影響**: 左→右表示や表紙単独表示は未実装。設定を追加する場合はページ組の計算とキャッシュ要求を変更する。

## ADR-012: 設定画面は作らず TOML を直接編集する

**決定**: GUI の設定画面を持たず、設定は TOML ファイルで行う。メニューは表示モードと全画面など、頻繁に使う操作に限定する。

**理由**: 設定 UI の実装とプラットフォーム差を避け、コアの閲覧機能に集中する。

**影響**: 設定の discoverability は README と生成される既定ファイルで補う。設定変更の反映は次回起動時。

## ADR-013: エラーは文字列 / Box<dyn Error> で扱う

**決定**: ライブラリ内の失敗は主に `String`、CLI とヘッドレスは `Box<dyn Error>` で扱う。`anyhow` / `thiserror` は導入しない。

**理由**: 現状のエラーは表示用メッセージが中心で、型付きエラー階層の利点が小さい。

**影響**: エラーの型で分岐する処理は書けない。必要になった時点で導入を再検討する。

## ADR-014: CLI は自前パーサ

**決定**: `--list`、`--check`、`--render-page`、`--prefetch`、`--help` を小さな自前パーサで処理する。`clap` は導入しない。

**理由**: 引数が少なく、依存とコンパイル時間を増やす利点が小さい。

**影響**: オプションの組み合わせやエラーメッセージは自前で維持する。

## ADR-015: Windows 7 はコードと手順を用意し、実機検証は別途行う

**決定**: `x86_64-win7-windows-msvc` 向けのビルド手順を README に記載する。実機検証は未実施のまま、macOS での動作確認を優先する。

**理由**: Win7 は Tier 3 ターゲットで nightly と `build-std` が必要。開発環境での継続的な検証コストが高い。

**影響**: Windows 7 対応を「保証済み」とは表現しない。リリース前にクリーン VM での確認が必要。

## ADR-016: 依存は最小限。Stars は参考値として扱う

**決定**: 新しい依存は、保守状況、ライセンス、OS 互換性、代替実装のコストを総合して判断する。初期設計の「GitHub Stars 750以上」は目安とし、機械的な足切りにはしない。

**理由**: 実際に採用した `zip` / `image` / `winit` / `softbuffer` / `muda` / `dirs` / `serde` / `toml` のすべてが同じ基準を満たすわけではない。一方で、これらを自前実装するコストの方が高い。

**影響**: 依存追加時は理由をこの文書に追記する。Stars だけで安全性や保守性を判断しない。
