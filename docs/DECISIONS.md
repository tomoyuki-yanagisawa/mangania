# MangaNia 技術判断

更新日: 2026-11-17
形式: 追記式の ADR（Architecture Decision Record）

現在の構成は [DESIGN.md](DESIGN.md)、既定値は [PREFERENCES.md](PREFERENCES.md) を参照してください。

## ADR-001: UI は winit + softbuffer + muda

**背景**: 初期設計では libui-ng を候補にしていたが、ZIP のドラッグ＆ドロップ、ネイティブメニュー、CPU 描画を小さくまとめたい。

**決定**: `winit` でイベントループとウィンドウ、`softbuffer` で CPU 描画、`muda` で Windows / macOS のネイティブメニューを実装する。

**理由**: 画像ビューアに必要な機能へ直接アクセスでき、libui-ng の FFI とビルド依存を避けられる。Win7 向けのビルド経路も比較的単純になる。

**影響**: メニューは Windows / macOS のみ。Linux はキーバインドでの操作になる。UI 部品は自前で最小限にする。

**更新 (ADR-026)**: `muda` は削除し、メニューは Windows の Win32 と macOS の AppKit を `src/platform/` で直接扱う。共通部分は `MenuCommand` / `MenuState` だけにした。

## ADR-002: ZIP は zip crate で直接読む

**背景**: 初期設計では libarchive を暫定候補にしていた。

**決定**: `zip` crate を使い、Central Directory を一度だけ索引化してエントリへランダムアクセスする。Stored / Deflate のみを対象とする。

**理由**: ZIP / CBZ に必要な機能へ絞れば依存が小さく、外部 C ライブラリのビルドと Win7 互換性の確認が不要になる。

**影響**: RAR / 7z は対象外。ZIP64 や破損データの扱いは crate と自前の上限チェックに依存する。

## ADR-003: 画像は image crate、JPEG / PNG / WebP / BMP のみ

**決定**: `image` crate の JPEG / PNG / WebP / BMP デコーダを使い、デコード結果を `RgbaImage` に統一する。

**理由**: まず漫画ビューアとして必要な形式を確実に扱う。外部 C デコーダの FFI を持たずに済む。

**影響**: JPEG 2000、JPEG XL、AVIF、GIF は未対応。縮小デコードは行わず、原寸デコード後に表示サイズへ縮小する。

## ADR-004: 描画は CPU のピクセルバッファ

**決定**: デコード済み画像を `u32` の 0RGB バッファへ描画し、`softbuffer` でウィンドウへ転送する。

**理由**: GPU を必須にせず、Win7 を含む環境で描画経路を単純に保てる。画像ビューアの表示要件では GPU 描画の利点が小さい。

**影響**: 大きな画像の縮小は CPU で行う。表示中は直前のフレームを保持して暗転を防ぐ。

## ADR-005: 自然順ソートは自前実装

**決定**: ファイル名の数字列を数値として比較する自然順ソートを自前で実装し、テストする。

**理由**: `2.jpg` と `10.jpg` の順序は漫画ビューアの基本要件。小さな処理であり、依存追加よりテストで固定する方が扱いやすい。

**影響**: 大文字小文字を同一視し、数字列の先頭ゼロを無視する。仕様を変える場合は `archive.rs` のテストを更新する。

## ADR-006: 設定は TOML を3ファイルに分ける

**決定**: 一般設定を `config.toml`、キーを `keybindings.toml`、マウスを `mouse.toml` に分ける。`serde` + `toml` で読み書きする。

**理由**: 文字列とパスを扱うため手書きパーサでは不足する。設定の責務を分けると、ユーザーが編集する範囲とコードの担当範囲が明確になる。

**影響**: 設定ディレクトリは `dirs` で解決する。キー・マウス設定は初回起動時に既定値で作成する。

## ADR-007: 保存は元画像バイト列をそのまま書き出す

**決定**: 表示中ページの保存では、ZIP 内の元エントリを読み直し、再エンコードせずに書き出す。拡張子は元画像から引き継ぐ。

**理由**: 画質を落とさず、保存処理も単純になる。

**影響**: 保存のたびに ZIP を開き直して索引を作る。大きな書庫では保存に少し時間がかかる。同名ファイルは上書きする。

## ADR-008: 入力は Action に集約し、キー・マウスを設定可能にする

**決定**: メニュー、キーボード、マウスの操作を `Action` に集約し、キーとマウスの割り当てを TOML で変更できるようにする。

**理由**: 操作ごとに実装が分岐すると、メニューとキーの挙動がずれる。設定可能にしても実装の中心を1箇所に保てる。

**影響**: アクション名と既定値の互換性を維持する必要がある。設定ファイルにないアクションは既定値を使う。

## ADR-009: ダブルクリックは保留と遅延で判定する

**決定**: ダブルクリック設定があるボタンでは、シングルクリックのアクションを `double_click_ms` の間だけ保留する。2回目が時間内・近距離ならダブルクリックのアクションだけを実行する。

**理由**: 左クリックが「次のページ」、ダブルクリックが「保存」の場合、シングルクリックを即時実行すると保存前にページが進んでしまう。

**影響**: ダブルクリックを割り当てたボタンは、シングルクリックの反応が判定時間だけ遅れる。ダブルクリックのないボタンは即時のまま。

## ADR-010: 先読みは1ワーカー、キャッシュはページ数とバイト数で制限

**決定**: ZIP 読み出しとデコードを1つのワーカースレッドで行い、現在ページと表示相手を1つのバッチとして優先する。キャッシュは `cache_pages`（既定8ページ、1ページ1枚）と `cache_mb`（既定128MiB）のどちらかに達するまで保持し、両方とも `config.toml` で変更できる。`prefetch` は単ページ表示ではページ数、見開き・混合表示では2ページ単位の段数として扱う。`--prefetch` は `config.toml` の `prefetch` を上書きする。

**理由**: 実装を小さく保ちながら、ページ送りの待ち時間とピークメモリを制御できる。既定値はそのままに、環境に応じて調整できるようにする。

**影響**: 同時デコードは行わない。巨大な画像は先読みせず、現在ページだけを保持する。`cache_pages = 0` と `cache_mb = 0` は既定値として扱う。展開済みエントリの保持方法は ADR-023 を参照。

## ADR-011: 見開きは右→左固定、組は先頭から (1,2)

**決定**: 見開きは現在ページを右、次ページを左に置く。ページ送りは2ページ単位とし、末尾で1ページ余る場合は右セルに表示して左セルを空白にする。

**理由**: 日本の漫画の読み方向に合わせた最小の実装とする。

**影響**: 左→右表示や表紙単独表示は未実装。設定を追加する場合はページ組の計算とキャッシュ要求を変更する。

## ADR-012: 設定画面は作らず TOML を直接編集する

**決定**: GUI の設定画面を持たず、設定は TOML ファイルで行う。初回起動時にコメント付きの `config.toml` を既定値で書き出し、設定画面の代わりにする。メニューは表示モードと全画面など、頻繁に使う操作に限定する。

**理由**: 設定 UI の実装とプラットフォーム差を避け、コアの閲覧機能に集中する。コメント付きの既定ファイルがあれば、項目を探しやすく、そのまま編集できる。

**影響**: 設定の discoverability は README と生成される既定ファイルで補う。設定変更の反映は次回起動時。

## ADR-013: エラーは文字列 / Box<dyn Error> で扱う

**決定**: ライブラリ内の失敗は主に `String`、CLI とヘッドレスは `Box<dyn Error>` で扱う。`anyhow` / `thiserror` は導入しない。

**理由**: 現状のエラーは表示用メッセージが中心で、型付きエラー階層の利点が小さい。

**影響**: エラーの型で分岐する処理は書けない。必要になった時点で導入を再検討する。

## ADR-014: CLI は自前パーサ

**決定**: `--list`、`--check`、`--render-page`、`--prefetch`、`--help` を小さな自前パーサで処理する。`clap` は導入しない。

**理由**: 引数が少なく、依存とコンパイル時間を増やす利点が小さい。

**影響**: オプションの組み合わせやエラーメッセージは自前で維持する。

## ADR-015: Windows 7 はコードと手順を用意し、実機検証は別途行う

**決定**: `x86_64-win7-windows-msvc` 向けのビルド手順を README に記載する。実機検証は未実施のまま、macOS での動作確認を優先する。

**理由**: Win7 は Tier 3 ターゲットで nightly と `build-std` が必要。開発環境での継続的な検証コストが高い。

**影響**: Windows 7 対応を「保証済み」とは表現しない。リリース前にクリーン VM での確認が必要。

## ADR-016: 依存は最小限。Stars は参考値として扱う

**決定**: 新しい依存は、保守状況、ライセンス、OS 互換性、代替実装のコストを総合して判断する。初期設計の「GitHub Stars 750以上」は目安とし、機械的な足切りにはしない。

**理由**: 実際に採用した `zip` / `image` / `winit` / `softbuffer` / `muda` / `dirs` / `serde` / `toml` のすべてが同じ基準を満たすわけではない。一方で、これらを自前実装するコストの方が高い。

**影響**: 依存追加時は理由をこの文書に追記する。Stars だけで安全性や保守性を判断しない。

## ADR-017: CI とリリースは GitHub Actions

**決定**: Pull Request と main への push で、Ubuntu / macOS / Windows の3環境で `cargo fmt --check`、`cargo clippy --all-targets`、`cargo test` を実行する。バージョンは `Cargo.toml` の `[package] version` を唯一の情報源とし、main へのバージョン更新マージで `v<version>` タグと GitHub Release を自動作成する。成果物は Windows zip、macOS tar.gz、Linux tar.gz とし、Release notes は前回タグからのコミットタイトル一覧を使う。

**理由**: バージョン管理とリリース作業を手作業から減らし、PR ごとにクロスプラットフォームのテストを回すため。

**影響**: Windows 7 向けの `build-std` 成果物は自動リリースには含めない。必要になった時点で別ジョブとして追加する。タグが既に存在するバージョンではリリースをスキップする。

## ADR-018: Enter と中クリックを既定の操作にする

**決定**: `Enter` を全画面表示の切替に追加し、中クリックを1ページ送り（`next_single`）に割り当てる。見開き中の中クリックは開始ページを1つずらし、通常の2ページ送りはその偶奇を保って進む。

**理由**: 要求された操作を設定ファイルの編集なしで使えるようにする。見開きの組を1ページ単位で調整できると、見開きの境界を確認しやすい。

**影響**: 見開きの現在ページが奇数開始になり得る。見開き表示へ切り替えるときは従来どおり偶数ページに揃える。

## ADR-019: Windows 7 版をリリースに含める

**決定**: ADR-017 のリリース範囲を広げ、`x86_64-win7-windows-msvc` の `build-std` ジョブを Release workflow に追加する。`windows7-x86_64` の zip を添付し、CI でも同じターゲットのビルドを確認する。

**理由**: 通常の `x86_64-pc-windows-msvc` ビルドは Rust 1.78 以降 Windows 10 の `ProcessPrng` を要求するため、Windows 7 では起動できない。実機で確認できる Win7 成果物を継続的に出す必要がある。

**影響**: nightly と rust-src に依存する。Tier 3 ターゲットのため、実機検証と nightly の変化には注意が必要。Windows 7 では Universal CRT 更新が別途必要。

## ADR-020: Windows 7 のビルド確認は Release 時のみ行う

**決定**: ADR-019 のうち、PR / main push の CI で Win7 ターゲットをビルドする部分をやめる。Win7 ターゲットのビルドは Release workflow の `build-win7` ジョブだけで行う。

**理由**: PR の CI で生成した artifact は GitHub Actions から取得する必要があり、Windows 7 実機ではログインできないため検証に使いにくい。バージョン bump の Release で公開される zip なら Win7 から直接ダウンロードできる。PR ごとの nightly + `build-std` のコストも削減できる。

**影響**: Win7 ターゲットのビルド破損は Release まで気づかない可能性がある。必要なら手元または一時的な workflow で確認する。

## ADR-021: パス解決と形式判定は `open.rs`、ZIP の索引は `archive.rs`

**背景**: Windows ショートカット（`.lnk`）の解決が `archive.rs` に混在し、アプリ・ヘッドレス・保存の各入口が `Archive::open` を直接呼んでいた。非 ZIP は zip crate の EOCD エラーがそのまま見えていた。

**決定**: `src/open.rs` に `.lnk` 解決、形式検出、共通の `Entry` API を置く。`Archive` は ZIP の索引化とエントリ読み出しだけを担当する。`Entry::open` は解決済みのパスを返し、呼び出し側はそのパスを保持する。

**理由**: 入口処理を1箇所に集約して二重解決を避け、RAR/CBR・7z・HTML・空・破損などの形式に応じた明確なエラーを返せる。ZIP の読み込み・安全チェックは従来の実装を維持できる。

**影響**: 非 Windows の `.lnk` エラーは従来どおり。自己解凍形式のように先頭にデータがある ZIP は、先頭バイトだけで拒否せず zip crate の判定に任せる。RAR / 7z は引き続き未対応で、明示的なエラーになる。

## ADR-022: Windows は GUI サブシステム、CLI 時だけ親コンソールへ接続する

**決定**: Windows のバイナリに `windows_subsystem = "windows"` を適用し、引数ありの起動では `AttachConsole(ATTACH_PARENT_PROCESS)` で親コンソールへ接続する。既存の stdout / stderr / stdin が有効な場合は上書きせず、リダイレクトを維持する。コンソールがなければ GUI として動作する。

**理由**: ダブルクリック起動で黒いコンソールウィンドウを出さず、`--list` / `--check` / `--render-page` などの CLI 出力は従来どおり cmd / PowerShell から使えるようにするため。

**影響**: コンソールサブシステムではなくなるため、GUI 起動時の `eprintln!` は見えない。CLI 起動時に親コンソールがない場合も出力先がないため、必要ならダイアログやログを追加する。

## ADR-023: 展開済み ZIP エントリは専用ディスクキャッシュだけを使う

**背景**: 展開済みバイト列を `Vec` で保持すると、ページサイズに比例してメモリ使用量が増える。先読みと縮小キャッシュを併用すると、大きな ZIP ではピークメモリが読みにくくなる。

**決定**: ZIP エントリは OS ごとの専用キャッシュディレクトリへストリーム展開し、そのファイルから `image::ImageReader` で直接デコードする。ページ読み込みの経路はディスクキャッシュだけとし、メモリ読み出しへのフォールバックは持たない。キャッシュキーは ZIP パス・サイズ・更新時刻・エントリ番号・名前・CRC32・展開後サイズからハッシュを作る。ハッシュはツールチェーン更新で変わってよく、その場合はキャッシュが再生成される。ディスクキャッシュは自動削除せず、メニューの「キャッシュを削除」で手動削除する。ページ送り中に削除処理を走らせない。

**理由**: 原寸画像をメモリに残さず、ページ移動時の再展開コストも避けられる。キャッシュの失敗を隠さずページエラーにすることで、ディスク容量や権限の問題をユーザーが把握できる。

**影響**: キャッシュディレクトリに書き込めない環境ではページを表示できない。壊れたキャッシュファイルは削除してエラーにし、次にそのページを読むときに ZIP から再展開する。キャッシュには展開済みページ画像が残るため、プライバシー上不要ならメニューまたはディレクトリ削除で消す。容量は自動制限しない。

## ADR-024: 混合表示はページの向きだけで表示を決める

**背景**: 横長の見開きページを単ページで読みたいという要求がある。しかしページの向きはデコードするまで分からず、全体を通したペア境界を維持しようとすると、ナビゲーション・先読み・キャッシュが複雑になる。

**決定**: 表示モードを `single` / `spread` / `mixed` の3つにする。混合表示では、現在ページが横長（正方形を含む）ならウィンドウ全体の単ページ、縦長なら右半分のセルに表示する。次ページも縦長なら左セルに並べ、それ以外は左セルを空白にする。表示画像のサイズはページ自身の向きだけで決め、隣のページとの組み合わせでは再縮小しない。戻る操作は、直前の2ページがともに縦長なら2ページ、それ以外は1ページ戻る。

**理由**: ページの向きはデコード時に分かるため、先読みした範囲だけで表示を決められる。画像を向きごとに1枚だけ保持すれば、ペアの組み合わせが変わっても再生成が不要になる。全体のペア境界を保証しない代わりに、状態とキャッシュを単純に保てる。

**影響**: 混合表示で途中へジャンプした後は、順読み時とペアがずれる場合がある。`config.toml` の表示モードは `spread = true/false` から `mode = "single" / "spread" / "mixed"` に変わった。既存の `spread` キーは読み込まれない。

## ADR-025: ウィンドウをアクティブにするクリックは操作に使わない

**背景**: 非アクティブなウィンドウをクリックして前面に出したとき、そのクリックがクライアント領域のクリックとして届き、ページ送りとして実行されることがある。

**決定**: Windows ではウィンドウプロシージャをサブクラス化し、`WM_MOUSEACTIVATE` のヒットテストが `HTCLIENT` のときに `MA_ACTIVATEANDEAT` を返す。ウィンドウはアクティブになるが、アクティブ化したクリックは破棄される。タイトルバーなどクライアント領域外のクリックは従来どおり OS に任せる。Windows 以外では `Window::has_focus()` を使い、非アクティブ時のクリックを無視する。

**理由**: Windows のイベント順序では、クリックがアプリに届く時点でフォーカス済みになっている場合がある。`WM_MOUSEACTIVATE` は OS がアクティブ化クリックを破棄できる正規の入口で、フォーカス時刻や猶予時間のような推測が不要になる。プラットフォーム固有の unsafe コードは `platform/windows` に閉じ込める。

**影響**: Windows で非アクティブなウィンドウのクライアント領域をクリックすると、そのクリックではページ送り・保存などが実行されない。タイトルバーやすでにアクティブなウィンドウの操作は変わらない。ホイールによるページ送りは対象外。

## ADR-026: ネイティブメニューは OS の API を直接使う

**背景**: メニューを `muda` に任せると、OS 固有のメニュー挙動をアプリ側から制御しにくい。Windows のイベント順序、全画面時のメニュー取り外し、macOS のシステムメニューバーを、アプリの状態と直接結び付けたい。

**決定**: `muda` を削除する。OS 非依存の `MenuCommand` / `MenuState` だけを `platform/menu.rs` に置き、Windows は `CreateMenu` / `AppendMenuW` / `WM_COMMAND` と `SetWindowSubclass` を、macOS は `NSMenu` / `NSMenuItem` と target/action を `platform/` 配下で実装する。Linux は従来どおりメニューを持たない。メニュー操作は `UserEvent::Menu(MenuCommand)` としてイベントループへ戻し、実行とチェック状態の同期は `App` が行う。

**理由**: メニューの生成・表示・チェック状態をアプリの状態と同じ場所で扱える。Windows では全画面時に同一の `HMENU` を取り外して戻せる。macOS では標準のアプリケーションメニューを維持しつつ、ウィンドウ内メニューを持ち込まずに済む。依存も1つ減る。

**影響**: Windows と macOS のメニュー実装は自前で保守する。Windows のメッセージ受信はウィンドウごとの subclass に閉じ込め、macOS の AppKit 呼び出しはメインスレッドに限定する。キーボードショートカットは従来どおり `keybindings.toml` と winit が担当し、メニュー項目にはアクセラレータを付けない（終了の Cmd+Q を除く）。

## ADR-027: 既存の設定ファイルには不足キーだけを追記する

**背景**: 設定項目が増えても、既存の `config.toml` や `keybindings.toml` には新しいキーがない。ファイルを丸ごと再生成すると、ユーザーが設定した値、コメント、未知のキーを失う。何も追記しないと、新しい既定値が適用されているのか分かりにくい。

**決定**: 起動時に `toml_edit` で既存の TOML 文書を読み、既定テンプレートにだけ存在するキーを再帰的に追記する。既存の値、コメント、未知のキー、明示的な `[]` は変更しない。追記するのは、ファイルが TOML として読め、かつ現在の設定形式として解釈できる場合だけとする。壊れたファイルや解釈できないファイルは変更しない。変更が無ければ書き込まず、書き込みは既存の原子的保存を使う。

**理由**: 部分的な追記なら、ユーザーの編集内容を保ちながら新しい設定項目を発見できる。ファイル全体の再生成や、文字列置換による場当たり的な追記より安全で、コメントの位置も保てる。`toml_edit` は TOML の構文と装飾を保持するために必要な最小限の依存で、既に間接依存として存在していた。

**影響**: 既存の `double_click_ms = 400` は、既定値が 500 に変わっても 400 のまま残る。新しい既定値を使うには、ユーザーが値を変更するか、ファイルを削除して再生成する。設定の意味が不正なファイル（例: `mode = "invalid"`）は、値の保持を優先して追記しない。
