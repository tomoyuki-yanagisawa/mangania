## 実装追記（2026-11-12）

本設計に基づく Phase 1 の PoC を実装した。現時点の実装は以下。

- UI: libui-ng ではなく `winit` + `softbuffer` + `muda`（D&D とネイティブメニューのため）
- ZIP: `zip` crate。Central Directory の索引は一度だけ作成
- 画像: JPEG（ベースライン / プログレッシブ）、PNG、WebP。JPEG 2000 は対象外
- 操作: 「移動」「表示」メニュー、左右キー / クリック、ホイール、Home / End、1ページ / 見開き、全画面
- Windows 7: コードと `build-std` のビルド手順のみ。実機検証は未実施
- Linux: ネイティブメニューは未対応。`V` キーで表示モードを切替
- 自動テスト: 自然順、パス除外、PNG/JPEGデコード、1ページ/見開き描画、CLI、ヘッドレス確認、キャッシュ、ナビゲーション、Prefetch、設定TOML
- 開発用: `src/lib.rs` と `--list` / `--check` / `--render-page`（GUIなしで確認可能）

最新の使い方と詳細は `README.md` を参照。

## 1. 目的

MangaMeeya CE に着想を得た、高速・軽量なネイティブ漫画ビューアを Rust で新規実装する。重要なユーザー体験は「ZIPをすぐ開ける」「次ページが即座に出る」「メモリ不足で重くならない」。表示にGPUを必須としない。

### 要件と優先順位

1. Windows 7 SP1 x64 で実際に動くこと（Win7未満や全GPUの保証は不要）。
2. macOS（Apple Siliconを含む）と Linux で動くこと。
3. ZIP内の画像を直接閲覧できること。RAR/7zは範囲外。CBZはZIPと同じ技術で読めても独立した機能は作らない。
4. JPEG、PNG、WebPを最初にサポートし、JPEG XL、AVIF、JPEG 2000を段階的に評価する。
5. OS標準のボタン、チェックボックス等を利用するGUI。
6. デコード済み画像のメモリ量を制御し、ページ送りの待ち時間とピークRSSを計測する。
7. 外部依存の原則: GitHub Stars 750以上、保守継続、ライセンス・OS互換性。下位の推移的依存は監査し、750を満たさないRustバインディングは必要なら小さな自前FFIに置き換える。Starsだけで安全性は判断しない。

### 非目標

画像編集、動画、ネットワーク同期、サーバー、GPU独自レンダラ、RAR、独自ZIP実装の先行開発、プラグイン体系、初期段階での巨大なライブラリ管理機能。

## 2. 構成の結論

**UI: libui-ng（選定済み・技術検証前）**。ネイティブコントロールはGUIライブラリに任せる。libui-ngは2026年11月時点でGitHub約905 Stars、上流はmid-alpha。Windows 7対応の記載があるが、Rustツールチェーンを含む統合動作は未確認。Rust連携は薄いFFIをMangaNia側に持つ。画像描画はlibui-ngの描画コールバック/ネイティブペインをPoCで評価し、画像転送・スケーリングが成立しない場合に描画ペインだけOSごとの薄い実装とする。GUI全体をOSごとに作り直さない。

**Core: Rustの単一crate**。`App`、`Reader`、`ZipSource`、`Decoder`、`Prefetch`、`Cache`、`View`で責務を整理し、不要な抽象traitや多crate化は行わない。

**ZIP: Central Directoryで一度だけ索引を作り、閲覧順に各エントリを直接取り出す**。漫画の「順番に読む」はUX上の要求であり、ZIP先頭からの連続走査が高速とは限らない。自然順ファイル名とZIPの物理格納順は異なり得る。Stored/DeflateをMVPにする。ZIP64、CRC、異常データやパス名検証を実施。ライブラリは保守中で750スター以上のlibarchiveを暫定採用、ZIP専用のAPI/性能が要件に合わない場合は、維持可能な薄いZIP索引コード＋保守中の展開エンジン（libdeflateなど）をベンチマークで比較する。独自ZIPパーサ実装はリスクとして扱い、最後の手段とする。

**画像: CPUデコード中心**。JPEGはlibjpeg-turbo、基本形式はimage-rsまたは専用の成熟したデコーダ、JPEG XLはlibjxlを第一候補とする。アプリケーションからデコーダAPIを1層包み、形式判定・画像寸法確認・縮小デコード・ピクセル形式変換を共通化。CデコーダのFFIはポインタと所有権の境界を小さく保ち、unsafeは限定する。JPEG 2000はメンテ中で基準を満たす実装が見つかるまで保留し、「対応予定」と「対応済み」を区別する。

**表示: CPUピクセルバッファ → OS標準2D描画**。最初はリサイズ済みBGRA8/RGBA8等の表示用バッファを1枚保持。描画コールバックで余計な画像コピーを避ける。Macでは必要ならCore Graphics、WindowsではGDIなどを使い、UIイベントループをブロックしない。OS描画APIの実際の転送コストはPoCで計測する。

## 3. データフロー

```text
ZIPファイル
  ↓ Central Directory索引（1回）
自然順に並んだページ一覧
  ↓ 現ページを最優先する bounded queue
エントリ読み出し → Deflate展開 → 画像ヘッダー検査
  ↓
表示解像度を決定 → CPU画像デコード/必要なら縮小・色変換
  ↓
メモリ予算付き表示用バッファ（現在ページ＋小規模先読み）
  ↓
libui-ngの画像ペイン / OS 2D描画
```

### ページ管理

- `PageId` はアーカイブIDとエントリIDからなる。表示順は自然順ソートで確定（日本語名、連番、階層の扱いをテスト）。
- ナビゲーションはN+1/N-1、先頭/末尾、任意ページ移動に対応。最重要はN→N+1。
- ZIPの読み出しはランダムにエントリを選べる設計。先読み対象は閲覧方向に従い更新。
- ページ移動時は世代番号を更新し、古いデコード結果を破棄。外部Cデコーダの処理を無理に中断しない。

## 4. 先読み・省メモリ方針

### キャッシュ層

1. ZIP索引: 小さなメタデータのみ長期保持。
2. 圧縮画像バイト列: 必要時のみ保持。ZIP内JPEGはもともと圧縮済みなので、一時ディスクへのコピーは通常行わない。
3. 表示用画素: 現在ページを必ず保持し、次ページ1枚を優先して先読みする。余裕があればN+2/前ページを保持。
4. OSの表示リソース: CPUバッファと無駄に重複しないよう、実測で保持方針を決める。

初期設定はRAM内キャッシュ予算64MiB（低メモリ）または128MiB（標準）を提案。**これはプロセスの総RSS上限ではない**。デコーダの一時領域、ネイティブGUI、スタック、OS画像サーフェスを別途計測する。大判画像が予算を超える場合は先読みを止め、現在ページだけを優先する。

### デコードの順序

1. 画像ヘッダーで寸法を調べる。
2. 描画領域とDPI、ズーム倍率をもとに目標サイズを決める。
3. JPEGなど縮小デコード対応コーデックは、表示に必要な解像度を下回らない最大の縮小率を選ぶ。
4. 対応しないコーデックは原寸デコード→縮小が必要。ピークメモリが過大な場合は拒否または別方式を検討。
5. 拡大された場合だけ高解像度で再デコード。画質・ICC・Exif回転・アルファ処理を形式別にテスト。

### スレッド

- GUIメインスレッドではZIP解凍と画像デコードを行わない。
- 通常は先読み1ワーカー＋必要なら現在ページ優先の追加ワーカー。上限付きチャネルでジョブ数を制限。
- デコードの同時実行数はメモリ予算に応じて1〜2から開始。
- リクエスト世代番号により古い結果を表示させない。ページ送り中にキューが肥大化しないようする。
- `tokio`を最初から導入せず、stdスレッド・チャネル等の小規模構成を優先する。

### ディスクキャッシュ

MVPでは原則なし。ZIPは各エントリへ直接アクセスできるため、ディスクキャッシュが必ず有利とは限らない。HDDでの実測により必要になった場合だけ、容量上限、キーのハッシュ、ファイル更新時の無効化、クリーンアップを持つオプションとして実装する。

## 5. UI/UX

MangaMeeyaのように画像領域を最大化。標準部品のファイルオープンダイアログ、設定ウィンドウ、チェックボックス、メニューを用いる。

初期機能:
- ZIPファイルを開く、ドラッグ＆ドロップ（技術検証で確認）
- 左右キー／マウスでページ送り、全画面、ウィンドウサイズにフィット、原寸表示
- ページ番号と現在のZIPファイル名を表示
- 最小限の設定: 読み方向、ズーム、先読み、キャッシュ上限、ショートカット

後続機能:
- 見開き、右開き/左開き、閲覧位置保存、倍率・回転、詳細ショートカット

## 6. Windows 7 対応の工程

Rustの標準 `x86_64-pc-windows-msvc` ターゲットをWindows 7対応と誤認しない。`x86_64-win7-windows-msvc` はTier 3で、標準ライブラリの事前ビルドがなく`build-std`等が必要。macOSからのクロスコンパイルは最終目標とせず、まず再現可能なCI/Windowsビルド環境を確立する。C/C++ライブラリもWin7で使えないDLL/APIの依存がないことを確認する。

PoC合格条件:
- Windows 7 SP1 x64のクリーンVMでプロセスが起動する。
- libui-ngでネイティブ設定ダイアログを表示できる。
- ZIP内のJPEGを表示でき、左右キーで100ページ連続閲覧できる。
- macOS arm64、Linux x86_64で同一Coreが動く。
- Win7のGPU・ドライバを理由に起動失敗しない（独自GPU描画非必須）。

## 7. 計測とベンチマーク

ベンチ入力:
- 100/1,000ページZIP、Stored/Deflate、格納順と自然順が一致/不一致。
- JPEG 1200×1800/3000×4500、PNG、WebP、JXL。
- SSD/HDD、冷キャッシュ/温キャッシュ、RAM少量のWin7 VM。

計測:
- 起動時間、ZIP索引作成時間、先頭表示までの時間。
- `next()`操作から次ページが描画確定するまでのp50/p95/p99。
- 連続100ページ時のフレーム落ち、先読みヒット率、ピークRSS。
- ZIP解凍、画像デコード、色変換、縮小、描画転送の段階別時間。
- メモリ予算超過時の挙動、終了後の一時ファイル残存。

暫定目標: 先読みヒット時のページ切替p95 < 30ms、GUI入力のブロックなし。閾値はハードウェア・画面サイズに応じ実測で更新。起動時RSSに確約値を置かず、最新ベースラインから回帰検知を行う。

## 8. 安全性と保守性

- ZIPエントリ名をディスクへ直接展開しない。パストラバーサルを拒否。
- 画像ヘッダーの寸法、圧縮解除後サイズ、エントリ数に上限を設定し、整数オーバーフローを検査。
- 不正なJPEGやZIPでアプリ全体がクラッシュしないようエラー表示し、次ページへ進める。
- FFI境界を小さく保ち、ポインタのライフタイム、callback、所有権をコードレビュー。
- Fuzzテスト（ZIPメタデータ、画像ヘッダー）および破損データを使った回帰テスト。
- 依存の750スター基準・保守状況・ライセンスを依存採用時に記録。間接依存も保守状況を監査。
- Windows 7はサポート終了OS。ネットワークアクセスは不要にし、ローカルファイル閲覧に限定する。

## 9. ディレクトリ構成

```text
mangania/
├── Cargo.toml
├── Cargo.lock
├── rust-toolchain.toml
├── build.rs                 # libui-ng等のネイティブ依存

├── src/
│   ├── main.rs
│   ├── app.rs
│   ├── ui.rs                 # libui-ng FFIと薄い安全ラッパー

│   ├── archive.rs            # ZIP索引・読み出し
│   ├── decoder.rs            # codec呼び分け
│   ├── prefetch.rs           # ジョブスケジュール
│   ├── cache.rs              # 予算・退避
│   ├── view.rs               # 描画リソース管理
│   └── config.rs
├── tests/fixtures/
└── benches/
```

外部依存ごとにcrateを分けない。UIの相互運用箇所はOS別の最小モジュールに閉じる。

## 10. 実装順と検証ゲート

**Phase 0 / 互換性PoC（最重要）**
- Win7専用Rustビルド環境を確立。
- libui-ngのビルド・ネイティブ設定画面・描画領域をWin7/macOS/Linuxで確認。
- JPEG 1枚の表示・リサイズ・キーボード入力を確認。
- 判定: 3OSで成立しなければGUIスタック再評価（この時点でのみ）。

**Phase 1 / 最小閲覧機能**
- ZIP Central Directory読み出し、自然順、Stored/Deflate、JPEG/PNG/WebP。
- 左右ページ送り、画像フィット、エラー表示。
- 判定: ZIP内100ページを連続閲覧可能。

**Phase 2 / 省メモリ・高速化**
- libjpeg-turbo縮小デコード、先読みジョブ、メモリ予算、段階別計測。
- ZIP方式（libarchive/ZIP直読み）を同じ条件で比較し、速い方を選ぶ。
- 判定: 次ページ遅延・ピークRSSの回帰テストを導入。

**Phase 3 / 画像形式拡張**
- JPEG XL(libjxl)、AVIF、必要ならJPEG 2000の保守中実装を探索。
- 判定: Win7/macOS/Linuxで形式別フィクスチャが表示できる。

**Phase 4 / MangaMeeyaらしいUX**
- 見開き、読む方向、閲覧位置、カスタマイズ、配布パッケージ。
- 判定: Win7クリーンVMで依存DLLを含めた配布検証が通る。

## 11. 未確定事項（PoCで決める）

1. libui-ng描画領域からピクセルバッファをどれだけ低コストに表示できるか。upstream APIが不足する場合はOS別の画像ペインのみ薄く実装。
2. ZIPにlibarchiveを使うか。ZIP-onlyかつ次エントリアクセスが高速なら、より小さい方式に切り替える。
3. JPEG XL/AVIFのWindows 7依存DLL、SIMD命令、色管理の制約。
4. JPEG 2000は保守中の候補を確認するまで未対応。OpenJPEGを無条件採用しない。
5. 先読みとディスクキャッシュの適切な境界は実測で決める。
